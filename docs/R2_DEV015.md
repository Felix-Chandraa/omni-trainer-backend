# R2 DEV-015 — Flight Authority + Actual Control Path

## Scope

DEV-015 is the first milestone allowed to change the aircraft through the R2
training backend.

The path is:

    Student input
      -> authenticated training WebSocket
      -> server-owned Attempt/Aircraft assignment
      -> Active-state gate
      -> Flight authority owner + epoch
      -> generation
      -> per-station sequence
      -> client/server clock freshness
      -> schema/range validation
      -> narrow MAVLink adapter
      -> ArduPilot
      -> JSBSim
      -> FG authoritative state
      -> evidence recorder

Clients still do not receive a raw worker control port.

## Initial Flight commands

Only these command names exist:

- `flight_axes`
- `release_axes`
- `arm`
- `disarm`

There is no arbitrary MAVLink passthrough.

`flight_axes` is normalized:

- roll `[-1, +1]`
- pitch `[-1, +1]`
- yaw `[-1, +1]`
- throttle `[0, 1]`

and maps to RC channels 1, 2, 4 and 3 respectively.

## RC override safety

For MAVLink `RC_CHANNELS_OVERRIDE` channels 1-8:

- `0` releases that channel back to RC;
- `65535` ignores the field and therefore does **not** clear a previous
  override.

DEV-015 releases channels 1-4 with zero and ignores 5-8.

The server runs a 350 ms deadman. If fresh Flight axis commands stop, the
server releases RC override independently of the client.

Disconnect and server shutdown also release override. Shutdown then attempts
disarm before stopping the worker.

## Authority

One `flight` owner exists per Attempt in DEV-015. The lease contains:

- actor
- station
- aircraft / Attempt
- generation
- authority epoch

Takeover/handback increments the epoch. Commands carrying an old epoch fail
closed.

The current one-student demo grants the assigned Student the Flight lease once
the Attempt reaches Active. The manager API is designed so Instructor takeover
can replace that owner later without changing the command envelope.

## Command evidence

Continuous Flight samples distinguish:

- `accepted`: envelope/authority/schema valid;
- `forwarded`: an RC override frame was actually sent to the worker path;
- `applied`: only added when authoritative evidence confirms an effect.

DEV-015 automated acceptance confirms `applied` for the final throttle sample
only after FG records measurable ground displacement.

Arm/disarm uses MAVLink `COMMAND_LONG` and is considered applied only after the
vehicle heartbeat reflects the requested armed state. A command ACK without
heartbeat confirmation is not promoted to applied.

## Automated acceptance

The automated proof intentionally does not target takeoff.

1. Start one real managed ArduPlane+JSBSim worker.
2. Reach Ready and Active.
3. Grant Student Flight authority.
4. Prove a stale/wrong authority epoch is rejected.
5. Forward neutral Flight axes, then stop the stream and prove server deadman
   releases override.
6. Arm and confirm from heartbeat.
7. Send short staged throttle samples until FG proves at least 0.75 m of ground
   displacement, with an 80 m safety ceiling.
8. Release axes.
9. Disarm and confirm from heartbeat.
10. Finalize state, commands, authority, client evidence and `.tlog`.

## Feather manual controls

DEV-015 adds a small Flight Control panel to remote Feather mode.

The panel does **not** auto-arm or auto-enable controls.

- ARM: explicit arm transaction.
- ENABLE CONTROL: begins the 20 Hz axis stream with throttle at zero.
- RELEASE: stops streaming and releases RC channels 1-4.
- DISARM: explicit disarm transaction.
- `W/S`: throttle increase/decrease.
- Arrow Left/Right: roll.
- Arrow Up/Down: pitch axis.
- `A/D`: yaw.
- `X`: zero throttle and neutralize axes.

Window blur/hidden state disables the control stream; the server deadman remains
the final safety layer.

## Physical HOTAS

`Feather-Flight-main/hotas_client.py` reads Linux `/dev/input/js*` directly and
requires no evdev/SDL package.

List devices:

    python hotas_client.py --list

The client never arms the aircraft. It only streams axes after the mapped
throttle has remained <=5% for one second. Arm/disarm remains explicit in
Feather.

Axis indices vary by device, so the default `0/1/2/3` mapping is only a
starting point. A profile JSON or command-line axis/invert options can be used
without changing the backend authority contract.

## Still later

DEV-015 does not yet implement:

- production Instructor takeover UI;
- flight-mode/mission commands;
- GCS command gateway;
- final HOTAS calibration wizard/profile library;
- payload authority;
- pause/freeze control semantics.

Those build on the authority/command transaction contract proven here.
