# R2 DEV-014 — Real Feather Evidence + Replay Foundation

## Goal

DEV-014 closes the gap between the proven backend evidence path and the actual
Feather/Cesium client, then adds a read-only replay core.

The milestone is deliberately split into two gates.

### DEV-014A — Replay Core

A finalized Attempt evidence package is opened read-only. The reader verifies
indexed evidence files, loads `server/state` trajectory samples and produces a
time-ordered replay stream. ArduPilot and JSBSim are not started.

The replay gateway emits the same `omni.training.v1` telemetry envelope already
consumed by Feather `bus.js` and therefore reuses the existing `updateHUD()` and
Cesium aircraft pipeline.

Replay commands are a separate concept from aircraft commands. DEV-014A exposes
no aircraft command path. Any `cmd` message is rejected with
`replay_read_only`.

### DEV-014B — Real Feather/Cesium evidence proof

A real managed worker is started on the proven slot-1 runtime. The existing
Feather `remote_client.py` connects over loopback to the authenticated evidence
gateway.

The gateway records three distinct evidence views:

- `server/state`: authoritative FG trajectory/state;
- `clients/<station>/received_state`: what telemetry was actually acknowledged
  by the Student client;
- `clients/<station>/events`: what the Student client did or what UI events it
  generated.

This allows later debrief to distinguish "the aircraft did X" from "the Student
saw X" and "the Student did Y".

## Trust and identity

The client still sends only Student identity plus server-issued token. Station,
role, Attempt, aircraft and generation remain server-owned assignments.

For crew operation later, separate station principals can point to the same
aircraft/Attempt while retaining separate Flight/Payload evidence channels.

## Integrity compatibility

DEV-012 schema v1 hashes all indexed evidence. Its original finalization order
updated `manifest.json` after building the index, so old packages may show a
manifest-only checksum/size warning. DEV-014 accepts that single known metadata
compatibility case but strictly rejects mismatches in trajectory, tlog, client
evidence or any other indexed file.

Future recorder revisions should finalize manifest metadata before calculating
the index checksums.

## Replay source of truth

Replay uses stored `server/state` trajectory. It never attempts to reproduce a
flight by replaying HOTAS input into the FDM.

Client evidence and server events are retained as timeline overlays for later
review UI. They do not drive physics during replay.

## One-PC launchers

`run_dev014_feather_live_proof.sh`

Starts one real worker and recorded LAN server, waits for server credentials,
opens the existing PyQt Feather/Cesium remote client, then finalizes the Attempt
when the Feather window closes. The result reports received-state count,
client-event count, clock samples, tlog frames and the evidence package path.

`run_dev014_replay.sh [optional evidence package]`

Starts the read-only replay gateway, launches the same Feather/Cesium client and
loops the stored trajectory. No ArduPilot/JSBSim worker is launched.

Use `OMNI_REPLAY_SPEED=2` for 2x playback, etc.

## Not claimed yet

DEV-014 does not yet provide the final Instructor review timeline UI, arbitrary
seek/scrub controls, competency findings, physical HOTAS capture or production
crew assignment. Those build on this replay/evidence foundation.
