# R2 DEV-010 — Full 1 Instructor + 3 Students Concurrent Runtime Proof

DEV-009 proved two concurrent live Sessions/Workers and demonstrated that
stopping Worker A did not disturb Worker B.

DEV-010 uses the already-implemented three-slot pool to prove the full software
expansion target:

- one Instructor actor;
- three independent Sessions;
- three independent Attempts;
- aircraft `omni-1`, `omni-2`, `omni-3`;
- runtime slots / SITL instances 1, 2, 3;
- three direct ArduPlane + JSBSim + MAVProxy worker stacks.

## Acceptance sequence

1. Create three Sessions/Attempts and claim slots 1/2/3.
2. Start A, B, C while previously started workers remain healthy.
3. Each reaches Ready using its own fresh FG/MAV evidence.
4. Each revalidates and reaches Active.
5. All three must be Active at the same time.
6. All three FG streams must advance during the overlap window.
7. End/stop A:
   - A ports released;
   - B and C remain Active;
   - B and C telemetry continues.
8. End/stop B:
   - B ports released;
   - C remains Active;
   - C telemetry continues.
9. End/stop C.
10. All leases released and all three slot port bundles reusable.

## Cleanup verification ordering

The live verifier keeps one `FGObserver` UDP socket open per runtime slot while
collecting telemetry. Full slot reusability must therefore be checked only
after those observer contexts are closed. A test-owned FG socket is not an
orphan simulator process.

DEV-010 rev3 explicitly closes the observer `ExitStack` before asserting that
all three port bundles are reusable.

## Resource evidence

DEV-010 records a small observational resource snapshot while all three are
Active: host load average, available memory, and supervisor RSS.

These measurements are evidence only. They are not yet a performance
requirement or acceptance threshold. Performance/load qualification belongs to
hardening/acceptance after the functional 1+3 proof.

## Scope

Passing DEV-010 proves concurrent runtime/session isolation for the 1+3
software architecture. It does not yet prove:

- three physical student client PCs;
- three independent visual clients;
- three HOTAS devices/control-authority paths;
- payload workflows;
- WAN/LAN deployment performance;
- training workload/performance acceptance.
