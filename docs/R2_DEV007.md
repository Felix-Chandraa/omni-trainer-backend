# R2 DEV-007 — Worker Readiness + Session Integration

## Purpose

DEV-006 proved that an owned AircraftWorker can start the actual OMNI
ArduPilot/JSBSim runtime, receive raw FGNetFDM and raw MAVLink, remain stable,
and perform scoped cleanup.

DEV-007 connects that runtime evidence to the training state model.

An Attempt may move from `Setup` to `Ready` only after a trusted backend gate
verifies:

1. the Attempt, aircraft ID and generation match;
2. the worker PID is the exact process binding owned by the coordinator;
3. the worker is still `running` and `healthy`;
4. a valid raw FGNetFDM sample is fresh;
5. a receive-only MAVLink HEARTBEAT is fresh;
6. the evidence itself is fresh.

The gate then calls the existing SessionManager transition with
`readiness_verified=True`. A UI/client boolean is not treated as evidence.

## Deliberate limits

This is engineering readiness, not full training acceptance.

DEV-007 does **not** claim that these are already verified:
- HOTAS/physical-control readiness;
- payload readiness;
- instructor/student UI readiness;
- full authority transfer;
- full pause/resume semantics;
- mission/default-mission loading;
- scoring or assessment;
- visual-client readiness;
- multi-aircraft port allocation.

`Ready` also does not imply `Active`. Starting a training attempt remains a
separate instructor/state action.

## Freshness defaults

Engineering defaults for this slice:
- FG sample max age: 1.0 s
- MAV heartbeat max age: 2.0 s
- evidence bundle max age: 2.5 s

These are implementation guardrails for R2 and are not a final operational
requirement baseline.

## Acceptance

Offline:
- cumulative suite passes;
- stale/mismatched/unhealthy evidence fails closed;
- student cannot mark Ready;
- Ready does not auto-enter Active.

Live:
- start actual managed OMNI worker;
- collect raw FG and receive-only MAV heartbeat;
- verify worker identity/health;
- `Setup -> Ready` succeeds only through TrustedReadinessCoordinator;
- readiness audit events persist;
- worker cleanup releases SITL ports.
