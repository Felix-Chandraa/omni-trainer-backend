# R2 DEV-012 — Attempt Evidence Recorder

## Scope

DEV-012 is the recording foundation for later replay/assessment. It creates one
evidence package per Attempt and intentionally separates:

1. **Server truth** — authoritative simulator state/trajectory, raw MAVLink
   `.tlog`, lifecycle, commands/dispositions, authority and server events.
2. **Client experience** — per station/actor actions, received-state/UI/input
   evidence and client/server clock mapping.

The two are joined by Session/Exercise/Attempt/Aircraft/generation identity and
multiple time domains. Replay is not implemented in DEV-012.

## Time model

Every server evidence record carries:
- server UTC;
- server monotonic timestamp;
- elapsed monotonic time from recorder start;
- nullable simulation time;
- nullable active training time.

Client events also carry the client timestamp, mapped server monotonic time and
mapping uncertainty when clock-sync evidence exists.

DEV-012 does not invent simulation time before an authoritative source exists.

## Storage model

    evidence/<attempt-id>/
      manifest.json
      index.json
      server/
        aircraft.tlog
        state.000001.jsonl
        lifecycle.000001.jsonl
        events.000001.jsonl
        commands.000001.jsonl        # when used
        authority.000001.jsonl       # when used
      clients/
        <station>/
          clock.000001.jsonl
          received_state.000001.jsonl
          events.000001.jsonl

JSONL channels are append-only and segmented. Finalization records file size
and SHA-256 checksum. Queue drops create explicit gap intervals, mark the affected channel and the
whole package incomplete; the flight/control loop is not intentionally blocked
by disk I/O. Client received-state is stored separately from client actions so
review can distinguish server truth from what the student actually received.

## MAVLink `.tlog`

The server owns the worker's MAV client UDP output and stores each complete
MAVLink v1/v2 frame as a timestamped tlog record. The readiness verifier remains
on the separate monitor UDP output. This preserves a single authoritative
MAVLink record per aircraft/Attempt and avoids exposing raw ArduPilot control
ports to student stations.

A later GCS gateway can fan out from the backend instead of competing for the
worker's recorder port.

## Crew attribution

Client event records include actor, station, role and scope. Therefore one
aircraft may record:

- Student A / FLIGHT / station-flight
- Student B / PAYLOAD / station-payload

or even two Flight-role stations, while keeping their attempted actions
distinct. Whether a command was accepted/applied/rejected belongs to the
server command-disposition channel and is not inferred from client input.

## Fault semantics

Recorder overload or recording-only failure is evidence degradation, not an
automatic student failure. The package is marked incomplete/gapped for review.
Control/supervision failures remain governed by their own Attempt fault policy.

## DEV-012 live acceptance

The engineering live trial must prove:
- real worker reaches Active;
- real FG state samples are persisted;
- real MAVLink frames produce a non-empty `server/aircraft.tlog`;
- lifecycle records are persisted;
- two client-attribution fixture records are persisted but explicitly labelled
  as fixtures and never sent to the aircraft;
- final index/checksums are created;
- worker/recorder cleanup releases the runtime slot;
- no flight command is sent.

This does **not** yet prove real HOTAS/client event ingestion or replay UI.
