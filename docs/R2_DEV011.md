# R2 DEV-011 — LAN Client Protocol + Cesium Session Routing

## Goal

Expose the proven 1+3 server runtime to remote Student PCs without allowing a
client to connect directly to ArduPilot/JSBSim internal ports.

## Trust boundary

A Student client does not choose its aircraft, runtime slot, SITL port, or
Attempt. The backend issues an opaque token for one server-owned assignment:

Student -> Session -> Attempt -> Aircraft -> generation.

The client presents `student_id + token` in the `hello` frame. The server
returns the assignment. Telemetry frames carry the same routing identity and
the browser rejects mismatched Attempt/Aircraft/generation data.

DEV-011 is read-only. Remote `cmd` frames are rejected.

## Protocol

Default endpoint: TCP 9100, WebSocket protocol `omni.training.v1`.

Client hello:

```json
{
  "type": "hello",
  "protocol": "omni.training.v1",
  "role": "student",
  "student_id": "student-1",
  "token": "<server-issued>"
}
```

Telemetry carries `routing`, `seq`, normalized `data`, and `quality`.

## Cesium integration

Existing Feather already routes `updateHUD(data)` into
`updateAircraftOnMap()`. DEV-011 extends `src/js/bus.js` to authenticate to the
LAN gateway and feed the same normalized payload into that existing pipeline.
No second Cesium renderer is introduced.

## Network

Recommended deployment: wired Gigabit Ethernet.

- Server: Training Backend + ArduPlane/JSBSim workers + WS gateway.
- Student PC: local Feather static assets + Cesium view.
- SITL/FG/MAV worker ports stay internal to the server.
- Default LAN-facing training protocol port is 9100/TCP.

Current `map.html` loads Cesium JavaScript from CDN and uses Cesium World
Terrain/Ion. The visual therefore still needs Internet access for those
external resources unless Cesium/assets/terrain are self-hosted later. OMNI
telemetry itself only needs LAN.
