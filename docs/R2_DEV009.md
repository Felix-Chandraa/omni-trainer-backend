# R2 DEV-009 — Concurrent Multi-Worker Runtime

## Why DEV-009 does not reuse sim_vehicle.py as the concurrent owner

The legacy single-instance SDD explicitly prohibited two SITL instances because
the original runtime used fixed ports. The newer R2 architecture now requires
concurrent workers for the 1 instructor + 3 student expansion target.

Simply adding `-I 1`, `-I 2`, ... to the existing managed `sim_vehicle.py`
wrapper is not sufficient. `sim_vehicle.py` contains legacy name-based
`kill_tasks()` cleanup and registers cleanup at exit in versions relevant to the
current runtime. That behavior is unacceptable when Worker A and Worker B are
supposed to be isolated.

Therefore:

- legacy `run.sh` / `run_demo.sh` remains a **single-instance development path**;
- DEV-006/007/008 remain valid single-worker engineering evidence;
- DEV-009 concurrent workers use a **direct supervisor** and do not execute
  `sim_vehicle.py` at runtime.

## Runtime slot map

Slot 0 is intentionally forbidden.

| Slot | SITL TCP | SITL secondary | RC-in | FGNetFDM | MAV client | MAV monitor |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 5770 | 5772 | 5511 | 5513 | 14560 | 14565 |
| 2 | 5780 | 5782 | 5521 | 5523 | 14570 | 14575 |
| 3 | 5790 | 5792 | 5531 | 5533 | 14580 | 14585 |

ArduPilot's `-I N` shifts its SITL/FG/JSBSim ports by 10×instance. The OMNI
runtime allocator uses the same deterministic mapping and adds a dedicated
MAV monitor port per slot.

## Direct supervisor

Each AircraftWorker owns one `multi_worker_entry.py` process. That supervisor:

1. starts the proven ArduPlane binary directly with a non-zero instance;
2. uses an isolated working directory/eeprom;
3. copies the Omni-Trainer JSBSim aircraft directory into an isolated
   per-worker autotest directory, preventing shared reset.xml writes;
4. starts MAVProxy directly against that worker's SITL port;
5. keeps MAVProxy stdin open without accepting commands;
6. records exact ArduPlane descendant PIDs/start-times;
7. shuts down only those exact processes.

No `pkill`, `killall`, or name-based cleanup is used.

## Template derivation

DEV-009 does not guess the ArduPlane startup parameters. It extracts the exact
direct ArduPlane command printed by the most recent successful DEV-008/007/006
worker log, validates that it is `jsbsim:Omni-Trainer`, then changes only:

- the SITL instance;
- the isolated autotest directory.

This preserves the parameter/defaults command already proven on the user's
actual OMNI runtime.

## Lease model

`RuntimeSlotAllocator` stores a lock-protected lease table. A lease binds:

Session + Attempt + aircraft ID -> runtime slot.

The initial configured pool is 3 slots, matching the user's expansion target of
1 instructor + 3 students. Current delivery may still deploy only 1 instructor
+ 1 student.

## MAV probe isolation

DEV-009 invokes the existing receive-only `raw_mav_probe.py` directly for each
slot using that slot's own `--conn` address. It does not patch or import the
single-worker `omni_live_trial.raw_mav_probe` helper. DEV-006/007/008 remain
unchanged.

## DEV-009 live acceptance

The first live acceptance intentionally proves **2 concurrent workers**, not 3:

1. create Session A / Attempt A and Session B / Attempt B;
2. lease slot 1 and slot 2;
3. start direct Worker A and prove FG/MAV readiness;
4. keep A alive while starting Worker B;
5. prove both Ready, then both Active at the same time;
6. prove both FG streams continue during overlap;
7. End/stop Worker A while Worker B remains Active;
8. prove Worker B telemetry continues after A cleanup;
9. End/stop Worker B;
10. release both leases.

Only after 2-worker isolation passes should the same architecture be stress
tested with all 3 slots.
